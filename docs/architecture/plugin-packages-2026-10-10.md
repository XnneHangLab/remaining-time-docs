# 同仓库插件包与 SDK 边界 · 2026-10-10

## 版本与状态

游戏基线：`NevaMind-AI/remaining-time@b155e7c`（2026-10-10 读取的 origin/dev）。本文是设计方案和 SDK 首版范围说明，不宣称已经完成插件加载、小游戏、库存迁移或安全沙箱。历史架构依据见[世界架构](./world-model-2026-09-15)与[前后端分工](./client-server-2026-09-18)；旧文的运行方式只适用于各自提交。

目标：coding agent 开发一个玩法时，只依赖公开 SDK，不能为方便而引用或修改引擎内部实现。保留一个仓库和 `dev` 的即时构建部署，不要求另建仓库。

## 物理结构与发布

```text
engine/、agent/、src/、server/   宿主
packages/plugin-sdk/          独立 SDK 包
packages/blackjack/           后续具体玩法包（尚未实现）
```

采用 npm workspaces。宿主可以引用插件公开入口，插件只引用 SDK 和显式声明的第三方依赖；SDK 不引用宿主。禁止跨包相对路径、宿主路径别名和通过重新导出绕过边界。

SDK 自带 package.json、独立 tsconfig、ESM 与声明文件导出，可以复制到没有游戏源码的目录后单独构建、打包。首版是私有的 `0.1.0` 包，通过 tarball 分发，未发布 npm registry。游戏已有 build/deploy 命令保持原义，另加 SDK 构建命令；当前游戏尚未加载插件，所以不会因此自动出现新玩法。将来静态注册插件时显式增加所需构建顺序，仍由 dev 的同一流水线发布。

独立仓库不是隔离的前提。将来插件迁出仓库时，应保留同一个公开包依赖，而非复制引擎源码。

## SDK 0.1 的实际范围

SDK 只提供无宿主依赖的契约，不提供世界写入接口或新的同步服务。

| 类型 | 字段与含义 |
| --- | --- |
| `PluginManifest` | `id` 稳定插件 ID；`version` 插件版本；`apiVersion` 协议版本 1；`stateVersion` 状态格式版本，均必填 |
| `PluginSnapshot` | `plugin` 元信息；`instanceId` 活动/模块实例 ID；`revision` 已提交状态版本；`state` JSON 状态，均必填 |
| `ActionContext` | 宿主提供 `actorId`、`simulationTimeMs`（模拟毫秒）、`storyTimeSeconds`（世界秒），均必填 |
| `AvailableAction` | `id`、自然语言 `label`、JSON `payload` 必填；`description` 可选 |
| `PluginCommand` | `requestId`、`instanceId`、`expectedRevision`、`actionId`、`payload`，均必填 |
| `ActionResult` | 成功为 `ok: true`、完整新 `state`、`events` 数组；失败为 `ok: false`、`reason` |
| `PluginView` | `instanceId`、`revision`、该参与者可见的 `data` 与合法 `actions`，均必填 |

`RulePlugin` 定义 `create`、`actions`、`apply`、`view`。规则接收局部数据，返回结果；不获得 World、数据库、React 对象或任意状态路径写入器。UI 和 Jev 使用相同 action ID 与参数，自然语言标签只用于呈现，不反向解析为命令。

JSON 类型允许 null、布尔、有限数字、字符串、数组及对象；TypeScript 无法保证有限数字，也不能代替运行时校验。宿主适配器和插件入口必须验证外部输入。插件不得原地修改传入状态、读现实时间或偷偷调用模型；随机结果与外部结果必须通过可记录输入提供。

## 正式提交边界

以下是后续宿主适配器必须实现的职责，不是 SDK 类型自动提供的保证：

1. 从可信会话取得 actor 身份，检查插件及状态版本。
2. 按实例串行处理命令、检查 revision、按 requestId 去重。
3. 即使行动曾出现在候选列表中，也再次校验当前合法性。
4. 一起提交新状态与事件，失败不提交部分变化。
5. 存档记录插件版本、状态格式和提交位置。不兼容时明确拒绝或迁移。
6. 只向 UI/模型发送该参与者可见投影，不能把隐藏牌堆直接发过去。

正式插件状态由宿主托管，UI 的选中、动画可留在组件。插件不另建一份正式 localStorage 库存。回放使用已记录外部输出，不重新问模型；跨模块交易需要明确的提交协议，首版 SDK 不提供泛化 effect bus。

## 四类物品与规则模块

- 消耗品：库存负责数量；使用规则组合消耗、属性恢复与冷却。
- 任务物品：任务交付和物品收回一起提交；交出原物不清除已经发现的线索。
- 遗物：收藏/启用与具体能力分离。利息归经济规则，出老千归牌局认可的操作。独立 UI 不要求重复库存账本。
- 家具：区分资产定义与场景实例。装修产生摆放请求，空间系统检查碰撞、出口和角色占位，不维护第二张碰撞地图。

这些模块尚未迁入 SDK。当前 agentic 的物品记录由模型写入实体 `<items>` 与世界 `<player_items>`；已有结构化商店/库存则位于 MemoryWorld。迁移时要替换正式写入职责，而非让两份数量互相同步。自然语言继续承载物品意义、记忆和态度，不能再次改正式库存。God 也不能绕过同一规则。

## 小游戏、UI 与 NPC

Activity 仅指一次有开始、进行、结束或退出状态的局部活动，不要求独立服务。具体牌局规则在插件，参与者占用与退出由宿主接入。

21 点首版可以让 NPC 挂机，由固定策略处理出牌；Agent 只决定继续/退出并负责桌边对白，不把整副牌和复杂规则塞进普通 Agent 决策。NPC 可以不能离桌但仍能说话。退出先按牌局规则结算，再释放移动占用，恢复普通行为；旧的异步决策不得重新接管已退出或结束的局。

首版 SDK 的 `PluginView` 与 UI 框架无关。静态 React 接入可以沿用 GameFrame 的显示插槽，但适配器尚未实现。第三方代码未来可采用 iframe/Worker；同包执行不是安全沙箱，Worker 也不自动保证确定性或禁网。

## 对 coding agent 的约束

首版增加 CI：将 SDK 单独复制到临时目录，独立安装、构建、打包，再从消费者目录安装 tarball 并读取公开导出。这个检查证明 SDK 不依赖宿主源码，不等于已经限制所有未来插件。

后续增加首个实际插件时，需要一起补齐：插件依赖检查、独立消费者检查，以及插件 PR 跨入 engine/agent 等路径的合入限制。分支保护必须在 GitHub 设置中配置，工作流文件本身不能强制管理员禁止绕过。

最高强度的开发隔离是只给 agent 挂载插件目录，提供打包好的 SDK 与预览宿主。worktree 用于保留改动，并不是权限沙箱。宿主能力不足时另提宿主 API PR，发布新协议后再升级插件；不能把宿主改动伪装成插件内部实现。

## 下一步

先用一个独立 21 点包验证 UI、固定 bot、进入/退出、存档恢复与宿主适配，再扩展到库存与商店。不预建插件市场、动态发现、热卸载或通用技能效果语言。首版 SDK 是可以独立打包的契约起点，不是已经交付的完整 mod 平台。
